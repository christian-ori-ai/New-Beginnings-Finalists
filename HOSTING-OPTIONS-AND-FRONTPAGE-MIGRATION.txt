Hosting Options And FrontPage Migration Notes

Created: 2026-04-01

Working assumption
- The finalist demos in this repo are static HTML/CSS/JS sites.
- That means they are a strong fit for modern static hosting.
- I am assuming the current live site may still be edited or published from Microsoft FrontPage, and may still have old FrontPage-era hosting habits or dependencies.

Short recommendation
- Best simple path: GitHub Pages if the site is purely static and the team is comfortable with GitHub.
- Best polished static-hosting path: Cloudflare Pages if you want strong CDN/DNS handling and easy custom-domain setup.
- Best "marketing site" path with nicer non-developer tooling: Netlify.
- Best if the client wants the most familiar old-school hosting model: traditional shared hosting with cPanel or similar, using SFTP or File Manager instead of FrontPage publishing.

Why move away from FrontPage
- FrontPage and FrontPage Server Extensions are legacy technology.
- Microsoft documents that, as of December 18, 2010, FrontPage Server Extensions 2002 support for certain IIS 7-era installs was handled by Ready-to-Run Software rather than Microsoft.
- Microsoft also documents that IIS web services can be disabled during upgrade when FrontPage Server Extensions are installed, because of security concerns around FrontPage metadata and related files.
- Practical takeaway: it is safer to remove FrontPage-dependent publishing and features than to keep hunting for a host that still tolerates them.

Hosting options

1. GitHub Pages
Best for
- A brochure-style site with no real backend.
- A workflow where updates are made from the GitHub repo.
- Lowest ongoing cost and simplest stack.

Pros
- GitHub Pages is a static hosting service that publishes HTML, CSS, and JavaScript directly from a GitHub repository.
- Custom domains are supported.
- HTTPS is supported and can be enforced.
- Good fit with the new top-level GitHub repo that now exists for this project.

Watch-outs
- Static hosting only. No traditional server-side forms, databases, or FrontPage extensions.
- If contact forms are needed, they should be routed through a third-party form service or a small serverless function elsewhere.
- Best when one final site is chosen and published, rather than many variations at once.

My read
- This is the cleanest hosting target if the chosen site stays mostly static and the team is comfortable with GitHub.

2. Cloudflare Pages
Best for
- A static site with a custom domain and strong CDN performance.
- A setup where DNS and website delivery are managed cleanly.
- Teams that may want a little more room to grow later.

Pros
- Cloudflare documents that static asset requests on Pages are free and unlimited on both free and paid plans.
- Custom domains are supported.
- For a subdomain, Cloudflare documents that a custom CNAME can point the subdomain to the Pages site.
- Strong fit if the domain will eventually be managed in Cloudflare DNS anyway.

Watch-outs
- For an apex domain, Cloudflare documents that the site must be added as a Cloudflare zone and nameservers configured to Cloudflare.
- If the client wants to avoid nameserver changes right now, subdomain setup is simpler than apex setup.
- Forms still need a replacement path if the current site depends on FrontPage form handling.

My read
- Probably the strongest all-around modern hosting option for a static business site if the domain and DNS workflow are okay.

3. Netlify
Best for
- A static marketing site with a friendlier deployment and preview workflow.
- Teams that want drag-and-drop or Git-based deploys.
- Cases where form handling may be helpful without building custom backend code.

Pros
- Netlify's pricing page currently shows a free tier.
- Netlify also lists custom domains with SSL on the free tier.
- Netlify has a reputation for easy deploy previews and simple site management.
- Netlify pricing also explicitly includes form submissions as a metered capability, which is relevant if a contact form is needed.

Watch-outs
- Usage is credit-based, so it is worth watching the billing model if traffic, forms, or serverless features grow.
- Still not a FrontPage-compatible environment; any FrontPage-specific publishing or extensions need to be removed.

My read
- Good middle ground if the client wants something more user-friendly than raw GitHub Pages.

4. Vercel
Best for
- Teams that want polished previews, Git-based workflows, and room for more advanced frontend tooling later.
- A site that might eventually become more app-like.

Pros
- Vercel documents that its Hobby plan is free.
- Vercel documents that the Hobby plan includes built-in CI/CD, automatic HTTPS/SSL, and preview deployments for every Git push.
- Custom domains are supported and can be added to a project.

Watch-outs
- For a straightforward brochure site, this can be more platform than you actually need.
- If the final site stays plain static HTML/CSS/JS, GitHub Pages or Cloudflare Pages may be simpler.
- For a business site, plan fit should be checked carefully.

My read
- A valid option, but not my first recommendation unless the team especially likes the Vercel workflow.

5. Traditional shared hosting with cPanel or similar
Best for
- Clients who want a more familiar hosting account with a file manager, separate FTP/SFTP users, and email/web in the same general hosting relationship.
- Teams that do not want a Git-centered workflow.

Pros
- Closest mental model to the old FrontPage era: upload files, point a domain, manage through a hosting panel.
- cPanel documents that website files can be managed through FTP accounts or File Manager.
- This can be the easiest emotional transition for a non-technical client.

Watch-outs
- This should not be treated as "keep using FrontPage." It should be "host static files on a normal host."
- cPanel support notes that raw FTP is disabled by default in newer installs because of its age and vulnerabilities, so SFTP or File Manager is preferable.
- Quality varies a lot by hosting provider.
- You still need to replace FrontPage-dependent features.

My read
- Best if the client strongly wants a traditional host dashboard and no Git-based workflow.

Recommended host ranking for this project
- 1. Cloudflare Pages
- 2. GitHub Pages
- 3. Netlify
- 4. Traditional shared hosting with cPanel/SFTP
- 5. Vercel

Why that ranking
- These finalist sites are static.
- Static hosting is cheaper, simpler, safer, and easier to maintain than trying to preserve a FrontPage-era publishing model.
- Cloudflare Pages and GitHub Pages are the cleanest fit for the technical shape of these demos.

Migration steps from the current FrontPage setup

Phase 1: Inventory the current live setup
- Confirm who owns the domain registrar login.
- Confirm who controls DNS today.
- Confirm who has hosting access today.
- Confirm whether email is tied to the current web host or hosted elsewhere.
- Download a full backup of the current site before touching DNS or hosting.
- Archive the current FrontPage source files and the published server copy separately.

Phase 2: Identify FrontPage-specific dependencies
Look for anything that depends on FrontPage Server Extensions or old IIS behavior:
- Contact forms that email results through FrontPage extensions.
- Search boxes powered by FrontPage search.
- Guestbooks, discussion webs, hit counters, or old webbots.
- Shared borders, navigation bots, includes, or auto-generated theme pieces.
- Old `_vti_*` folders and metadata.
- Any ASP, CGI, or old script behavior that a static host will not run.

If any of those exist, replace them before cutover:
- Forms: use a modern form service or small serverless/API endpoint.
- Search: use a third-party search service or remove it if not needed.
- Counters/guestbooks/discussion features: retire them unless there is a real business need.
- Shared navigation/includes: replace with normal HTML, a template build step, or manual updates.

Phase 3: Choose the new hosting model
- If the final site is static and the team is okay with GitHub: choose GitHub Pages.
- If the team wants stronger CDN and cleaner DNS handling: choose Cloudflare Pages.
- If the client wants an easier non-developer publishing feel: choose Netlify.
- If the client wants a classic host dashboard: choose shared hosting with cPanel/SFTP.

Phase 4: Prepare the final site for launch
- Pick the final design direction from the finalist demos.
- Merge in any real business content, pricing, phone numbers, address details, and policy text.
- Make sure image paths, favicon files, and internal links are final.
- Make sure the mobile nav and contact links work on phones.
- Decide how the contact form will work, or remove it until a replacement is ready.
- Create a redirect map from old URLs to new URLs if the old site used different page names.

Phase 5: Set up the new host
- Create the project/account on the chosen host.
- Connect the repo or upload the site files.
- Test on the host's temporary URL first.
- Confirm assets load correctly and there are no broken links.
- Set the production branch or publish directory clearly.

Phase 6: Connect the domain
- Lower DNS TTL 24 to 48 hours before launch if possible.
- Decide whether the main public URL should be `www.domain.com` or `domain.com`.
- Point DNS to the new host.
- Turn on or verify HTTPS.
- Make sure apex-to-www or www-to-apex redirect behavior is correct.
- Keep email DNS records unchanged unless email is also being migrated.

Phase 7: Launch checks
- Test the homepage and every main nav page.
- Test on desktop and mobile.
- Test phone, email, and availability links.
- Test the contact form replacement.
- Verify no mixed-content warnings on HTTPS.
- Submit the site to Google Search Console and Bing Webmaster Tools if needed.
- Reinstall analytics and any conversion tracking.

Phase 8: Post-launch
- Leave the old host active for at least a short overlap period if budget allows.
- Keep a full backup of the old FrontPage-era site before cancellation.
- Monitor for 404s, missing images, and form issues during the first week.
- Document the new update workflow so nobody tries to publish from FrontPage again.

Other migration items to consider
- Domain verification and SSL ownership.
- Redirect rules for old page names.
- Privacy policy, cookie banner, and analytics compliance.
- Accessibility pass on headings, contrast, alt text, and keyboard nav.
- Image compression and page speed optimization.
- A very clear ownership list for domain, DNS, hosting, repo, and analytics accounts.
- A simple content update process for the client after launch.

What I would do here
- Choose one finalist as the production direction.
- Host it on Cloudflare Pages or GitHub Pages.
- Keep the domain at the current registrar unless there is a separate reason to move it.
- Keep email where it is unless email is causing problems.
- Replace any FrontPage-based forms with a modern form workflow.
- Archive the old FrontPage environment, but do not rely on it going forward.
