NEW BEGINNINGS
Hosting Options And FrontPage Migration Notes

Updated: 2026-04-18

Current business context
- Current traffic is light: roughly 600 users per month.
- Current bandwidth is also light: roughly 4 GB per year.
- Current hosting cost is about $400 per year with iPower.
- The current iPower subscription is expected to renew in June 2026, so any hosting decision needs to be made within roughly the next two months.
- The client is willing to spend up to about $500 per year for a better overall experience.
- The bigger decision is no longer raw hosting power. It is workflow: editing, reliability, SEO, customer management, and room to grow.

Working assumption
- The finalist demos in this repo are static HTML/CSS/JS sites.
- A lightweight internal content editor already exists in this repo for page content changes, but it is not yet a full live CMS, booking system, payments system, or client portal.
- The client currently uses Gigbuilder for some scheduling / client-event workflow. Meeting notes suggest this is around $39.99 per month. If that system is replaced internally, that budget can be redirected toward hosting and backend services.

Short recommendation
- Path 1 is the safest "keep costs stable" path: keep iPower, build an internal editor and admin workflow, and replace outside tools over time.
- Path 2 is the cleanest "modernize the stack" path: move the site to Netlify and build the same internal tools on a more modern hosting workflow.
- If the goal is simply to launch the new site quickly, either path can work.
- If the goal is to gradually evolve into a custom booking / client portal product, Netlify is the cleaner foundation.
- Because the renewal deadline is in June 2026, the realistic near-term decision is about hosting and launch readiness, not about completing every future feature before the renewal date.

Timing constraint
- As of 2026-04-18, there are only about 6 to 8 weeks to decide whether to keep iPower or move.
- That is enough time to launch a redesigned static site and make a hosting change if needed.
- That is probably not enough time to safely launch the full "perfect world" product in one pass if it includes admin tools, client logins, event records, notifications, and payments.
- The best use of the next two months is to separate the hosting decision from the larger product roadmap.

The two real paths

1. Stay on iPower and build an internal UI editor
Best for
- A lower-disruption launch.
- A client who wants to keep the current host relationship.
- A phased approach where the site goes live first and the richer tooling is added over time.

Estimated cost
- iPower hosting: about $400 per year.
- Domain: usually already bundled separately or already paid.
- If Gigbuilder is retired later, that may free up roughly $39.99 per month based on current meeting notes.
- Total annual hosting spend stays near the current number unless extra SaaS tools are added.

What this path can support
- Website content editing through an internal editor.
- Editable homepage / section content, images, pricing blocks, testimonials, and CTA copy.
- Internal admin dashboard for staff.
- Customer inquiry capture.
- Custom availability request flow.
- Event records for each client.
- Client login for managing event details such as song choices, venue, timeline, guest count, and notes.
- Online payments, if a payment provider such as Stripe is added.

Pros
- Lowest change management for the client.
- Keeps the current host and likely keeps the current DNS / registrar arrangement unchanged.
- Avoids a full hosting migration while the business is still deciding how much custom functionality it wants.
- Gives us room to build exactly the workflow they want instead of forcing their process into a third-party platform.

Watch-outs
- iPower is fine for brochure-site hosting, but it is not the reason the client gets a better UI. We would be responsible for building that better UI ourselves.
- Shared hosting environments can be less pleasant to manage for modern deployment workflows.
- Reliability is acceptable for a small site, but modern deployment previews, rollbacks, and versioned releases are usually not as clean as on newer platforms.
- If we build logins, event data, payments, or staff tools, we need to confirm what iPower supports well enough for the backend stack we choose.
- If the future app becomes more substantial, we may eventually outgrow the "just stay on shared hosting" model and migrate anyway.

My read
- This is a good path if the client wants familiarity and minimum disruption.
- It is less ideal if the custom portal becomes a meaningful product with authentication, structured event data, payments, and ongoing feature work.

2. Move to Netlify and build the internal tools there
Best for
- A modern static site with room to grow into a custom web app.
- Cleaner deployment, easier rollbacks, previews, forms, and domain management.
- A development workflow where we want a better foundation for future backend features.

Estimated cost
- Netlify site hosting can start well below the current iPower spend.
- Depending on plan and usage, the hosting layer could stay in the roughly $0 to $240 per year range before any add-on services.
- Domain costs still apply separately if not already owned.
- If Gigbuilder is retired, that budget can help cover auth, database, storage, email, payments, or scheduling services.
- Real cost depends less on page hosting and more on which backend pieces we add.

What this path can support
- Everything listed in Path 1.
- Better deployment workflow with previews and simpler release management.
- Serverless functions for custom form handling, availability checks, notifications, and API endpoints.
- Integration with external services for authentication, database, storage, CRM, payments, and email.
- A cleaner path toward a true client portal and internal admin tools.

Netlify strengths
- Strong fit for static or mostly-static sites.
- Easy deploys from Git, including previews before publishing.
- Good custom domain and HTTPS workflow.
- Friendlier for ongoing iteration than old-school shared hosting.
- Easier foundation if we want to gradually introduce custom backend behavior.

Netlify limitations and caveats
- Netlify is not an all-in-one business platform by itself.
- It does not automatically give the client a booking calendar, CRM, payment system, or customer portal. Those still need to be built.
- Authentication, structured event data, persistent storage, and payments generally require outside services or custom backend architecture.
- Metered usage matters once forms, functions, bandwidth, image processing, or background features grow.
- If the client wants a truly no-code admin experience, Netlify alone does not provide that. We would still need to build the admin UI.

My read
- Netlify is the better technical foundation if we are serious about building custom tools.
- The tradeoff is that it modernizes hosting, but it does not reduce the need for backend product work. It just gives that work a better home.

Future-state capabilities to keep in view

If we build beyond a brochure site, both paths should be evaluated against this future feature set:
- Website UI editing for the owners without touching raw code.
- Media management for photos, hero images, logos, and testimonials.
- Booking / availability workflow.
- Event intake form with date, venue, guest count, planner needs, DJ needs, and package selection.
- Client login to a single event dashboard.
- Client-managed event details: song choices, must-play / do-not-play, venue notes, timeline, introductions, special dances, and guest count updates.
- Staff-side event dashboard for internal notes and coordination.
- Email and text notifications.
- Contract acceptance and payments, if desired.
- SEO controls: page titles, meta descriptions, image alt text, indexability, redirects, and analytics.

Important architecture note
- Hosting and "business app" are separate decisions.
- A better host does not automatically create the admin experience the client wants.
- If the long-term goal is a polished internal system, the real scope is:
  site frontend + admin UI + authentication + database + notifications + optional payments + client portal.

What each path means for that future state

Path 1: iPower + custom internal tools
- Good if we want to launch quickly and add features carefully.
- Better if we want to preserve the current hosting relationship for now.
- More likely to feel transitional if the app becomes more complex.

Path 2: Netlify + custom internal tools
- Better if we want the site and future app on a cleaner modern deployment workflow.
- Better if we expect continuous iteration, previews, and releases.
- Better base if the client eventually replaces Gigbuilder with a custom solution.

Suggested recommendation language for the client
- Option 1: keep iPower and invest in a custom editing / client-management layer on top of the new site. This keeps hosting familiar and avoids a forced migration, while giving us room to replace Gigbuilder over time.
- Option 2: move to Netlify and use it as the new hosting foundation for the redesigned site plus future custom tools. This is the more future-friendly technical path, but it still requires us to build the actual booking, login, and payment features.

What I would do here
- If the immediate priority is launching the redesigned site with minimal disruption: keep iPower for phase 1.
- If the priority is setting up a cleaner long-term foundation for custom tools: move to Netlify.
- If the client is open to a phased approach, the strongest sequence may be:
  1. Launch the redesigned site.
  2. Add the internal content editor and lead capture workflow.
  3. Replace Gigbuilder only after the custom event dashboard is clearly scoped.
  4. Add login, event management, and payments as later phases instead of forcing all of it into launch.
- With the June 2026 renewal window in mind, my practical recommendation would be:
  1. Make the hosting decision first.
  2. Treat the first two months as a launch / migration window.
  3. Do not tie the renewal decision to a requirement that the full custom portal must also be finished by then.
  4. If there is any uncertainty about completing a clean Netlify migration in time, renew iPower for one more term and build phase 1 without schedule pressure.

Practical next-step questions
- Is the business emotionally attached to staying on iPower, or do they mainly care about ease of use?
- Do they want us to replace Gigbuilder soon, or only keep that possibility open?
- Do they need online payments in phase 1, or is inquiry + follow-up enough for now?
- Do they want staff-only editing first, or true client logins in the first release?
- Is email currently tied to iPower, and would moving hosting create any email risk?

Bottom line
- If this stays mostly a marketing site with a custom editor, iPower is workable.
- If this is heading toward a custom booking and client-management platform, Netlify is the better long-term host foundation.
- In either case, the major value will come from the internal tools we build, not from the hosting provider alone.
- The June 2026 renewal deadline makes a phased plan even more important: choose the host now, launch the redesigned site next, and treat the richer booking / login / payment system as a follow-on product phase unless the scope is intentionally kept very small.
